### 契约 / API

3. `packages/contracts/src/index.ts`：`BrandDto` 新增 `displayImageUrl?`（管理端返回，未上传时缺省）。
4. `apps/api/src/official-bags/brands-admin.service.ts`：
   - `toDto()` 改为 async，有 `displayImageKey` 时经 `cos.signedUrl()` 生成 `displayImageUrl`；
     `list()` 改为 `Promise.all` 映射。
   - 新增 `uploadImage()`：校验 content-type（jpeg/png/webp/heic/heif）与空 body；key 形如
     `brand/{id}/display/v{n}.{ext}`，**替换时换 key 而非覆盖**（key 自带 `v{n}` 版本，配合
     COS `CacheControl: immutable` 规避 CDN 长缓存旧图）；写 COS 后更新品牌字段，旧图交 `cleanup`
     队列删除，并写 `auditLog`（`BRAND_UPDATE_IMAGE`）。
   - 新增 `removeDisplayImage()`：清空 `displayImageKey`，旧图交 `cleanup` 队列，写 `auditLog`
     （`BRAND_REMOVE_IMAGE`）。
   - `remove()`：删除品牌时若存在展示图，一并交 `cleanup` 队列删除。
   - 构造函数新增 `CosService`、`QueueService` 依赖（二者为 `@Global()` 模块导出，无需改模块 imports）。
5. `apps/api/src/official-bags/brands-admin.controller.ts`：新增 `POST :id/image`（multipart 单文件，
   字段名 `file`）与 `DELETE :id/image`。

### 后台 UI

## 三、服务器容器内存硬限制（2GB 内存事故修复）

13. `infra/docker-compose.yml`：给所有容器补 `mem_limit`，并为 Node 进程加 `--max-old-space-size`，
    压低 PostgreSQL / Redis 内存参数，防止单个容器失控吃光物理内存 + swap 导致系统 thrashing 冻死：
    - `postgres`：`mem_limit: 512m` + 覆盖 `command` 压低 `shared_buffers` 等。
    - `redis`：`mem_limit: 256m` + `--maxmemory 200mb`（保留 `noeviction`，避免 BullMQ 任务被逐出）。
    - `api` / `worker` / `scan-worker`：`mem_limit: 512m` + `node --max-old-space-size=384`。
    - `migrate`：`mem_limit: 512m` + `--max-old-space-size=384`。
    - `admin`（nginx 静态站）：`mem_limit: 64m`。

> 这些是「上限」而非「预留」，总和仍略超 2GB，根治需升配内存（建议 8GB）；限制只是防单容器失控的兜底。

## 部署注意

- **迁移**：品牌展示图新增两张表列，推 main 后 CI 自动 `prisma migrate deploy`，无需手动跑。
- **CDN**：展示图 key 自带 `v{n}` 版本号且 `CacheControl: immutable`，替换是**换 key 而非覆盖**，
  无需刷 CDN。
- **小程序**：底栏 / 日历页 / 图标为前端改动，重新编译并发布小程序即生效，无后端改动。
- **内存限制**：`mem_limit` 与 `command` 属容器运行时配置，需重建容器生效（`docker compose up -d`
  会自动 recreate）；不涉及镜像重打包，但下次部署会随 compose 一并应用。
